# PokéCal UI review and alternative directions

Reviewed 14 September 2026. Scope: current implementation and a survey of better visual directions; no application changes.

## Recommendation

Use a compact analysis workspace as PokéCal's next direction. Linear's product interface is the strongest overall visual reference; Carbon supplies useful comparison-table patterns. Let Pokémon sprites and type colors carry the domain identity. The new visual system does not need to preserve Kraken's purple or give any replacement accent a brand-defining role.

The largest improvement is structural: put the result near the input that changes it. Recoloring the current page would preserve its long edit–scroll–read cycle.

## Current implementation

The implementation has a coherent foundation: shared tokens, restrained surfaces, native controls, explicit source information, useful numerical comparisons, and recognizable Pokémon imagery. The lookup identity block and desktop Builder's editor/result split are stronger than the calculator's long form. The app already has more personality and useful density than a generic dashboard.

The weak point is the allocation of attention and screen space. Large introductory headings precede every tool, global navigation looks like a group of raised action buttons, essential labels are unusually small, and setup controls frequently displace the analysis users came to see.

### Other observations

- The current purple is used for navigation, source strips, counts, summary values, numerical results, and selection. Too many roles therefore have similar emphasis. In a replacement system, choose the palette from the new workspace direction and use any accent narrowly for active selection and the result being examined.
- The desktop Builder already places output beside its editor. Preserve that relationship and reduce the large introductory area. Its phone layout loses the relationship when the entire editor comes first.
- Speed's ranked comparison is useful and product-specific. Give it more initial viewport space and keep active Speed/conditions visible near the rows. Its bounded scroll area is appropriate for dense comparison; replacing every row with a large card would make scanning worse.
- Teams uses tournament → player → Pokémon disclosures. This gives a useful browsing hierarchy. An optional tournament list/detail layout could reduce nesting during repeated exploration, but it is less urgent than the calculator.
- The Teams source strip reported an M-B archive while the first tournament title said M-C. The renderer uses archive-level format metadata (`src/ui/teams-page.js:64`). This needs a separate data/provenance check before treating it as a visual-copy fix.
- English move-effect descriptions in Traditional Chinese mode are intentional source content under the existing policy; translation coverage should not be confused with a styling defect.

## Alternative directions surveyed

The judgments below are recommendations for PokéCal, not claims that one design system is universally better. References are product interfaces or component guidance, not homepage styling. These can be implemented using the existing dependency-free HTML/CSS/ES modules; installing a design-system package is unnecessary.

| Direction | What it would look like in PokéCal | Best use | Tradeoff / verdict |
| --- | --- | --- | --- |
| **Linear-inspired compact workspace** | Quiet neutral canvas, fewer outer frames, compact title/navigation, strong alignment, selection expressed locally, clear distinction between toolbar and working content. | Overall app shell; Battle and Builder. | **Best overall direction.** Preserve readable labels and touch sizes instead of reproducing very small desktop controls. A permanent sidebar is not automatically necessary for six routes. |
| **Carbon-inspired analysis grid** | Broad comparison tables, clear column headings, aligned numbers, compact row spacing, filters close to the table, expandable detail. | Speed, Moves, Builder matchup results. | Best for numerical comparison. A literal Carbon visual copy could feel institutional; adopt its table discipline within PokéCal's identity. |
| **Sentry-inspired detail workspace** | A compact entity header, grouped editing actions, immediate outcome, and collapsible sections for secondary conditions or provenance. | Battle's complicated conditions; Teams' nested details. | Strong fit for progressive disclosure. Overusing drawers or nested disclosures would add clicks and hide battle assumptions. Always summarize active effects. |
| **GitHub Primer-inspired utility UI** | Familiar navigation, practical spacing, neutral borders, split list/detail views, conventional native-feeling forms. | Lookup and Teams; a conservative whole-app refresh. | Low-risk and understandable, but less distinctive. Pokémon content must supply the character. |

- [Linear: How we redesigned the Linear UI](https://linear.app/now/how-we-redesigned-the-linear-ui) — March 28, 2024. The product redesign emphasizes less visual noise, alignment, navigation density, and stronger hierarchy; its product screenshots were inspected.
- [Carbon: Data table usage](https://carbondesignsystem.com/components/data-table/usage/) — table toolbars, row sizes, width allocation, and expandable rows; the row-density reference image was inspected.
- [Sentry: New Issue Details UI](https://sentry.io/changelog/new-issue-details-ui-now-available/) — February 6, 2025. The explanation and annotated product screenshot organize workflow, context, results, and progressively disclosed detail.
- [Primer: Layout](https://primer.style/product/getting-started/foundations/layout/) and [view patterns](https://www.primer.style/product/scenario-patterns/view/) — responsive page structure and keeping list context while viewing details. Documentation surveyed; no signed-in GitHub workflow was tested.

### Proposed PokéCal direction

Choose the Linear-inspired workspace as the governing visual language, with Carbon's table behavior as supporting guidance. The useful changes are:

1. A compact global navigation bar and concise page titles.
2. Neutral work surfaces with fewer decorative color strips and raised wrappers.
3. Clear Pokémon identity, selected build, active conditions, and current result in the same working area.
4. Tables or aligned rows for comparisons, with detail expanded only when needed.
5. A phone layout designed around switching between setup and result, while retaining matchup context.

System fonts, semantic colors, Pokémon type colors, source distinctions, and native controls remain good choices. The brand palette is open: purple may be removed entirely. Palette selection still has less impact on task performance than fixing result placement.

Before adopting this across the app, compare a proposed Battle layout and Speed layout against the same existing states in English and Traditional Chinese at 1280 and 390. Battle tests editing complexity; Speed tests comparison density. No redesign has been applied in this review.

## Review method and limits

This is a direct browser/source survey. No independent-agent assessments or heuristic-score claims are included.

- Read `AGENTS.md`, `DESIGN.md`, `docs/ui-quality-workflow.md`, the local Impeccable and Web Interface Guidelines skills, relevant HTML/controller code, shared component code, and CSS rules.
- Inspected rendered first viewports for all six routes at 390px and 1280px in English and Traditional Chinese. Desktop captures used 720px or 800px height; phone captures used 844px. Inspected the calculator results and Speed ranking below the fold, and the calculator at 768px.
- Confirmed Lookup's no-match state, Arrow Down result focus, and Escape returning focus to the input and closing the popup. Used synthesized browser keyboard input. These checks do not establish full keyboard or screen-reader conformance.
- Observed Teams move from loading to the populated archive. Failure recovery was source-inspected but not forced in the browser.
- Browser: Codex in-app browser. Width changes emulate layout; physical-device touch and screen-reader testing were not performed. The full 320/1440 stress matrix and actual 200% browser zoom were not verified.
- Retrieved the living [Vercel Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md) on September 14, 2026. Upstream commit could not be resolved: shell networking failed DNS resolution and the web API request was unavailable. The fetched rules are not claimed to be pinned.
- Impeccable context and detector were actually attempted. Both failed because engine 0.1.5 was absent and the launcher could not create its cache. No detector pass or live overlay is claimed. Repository context and manual browser/source inspection were used instead.
- No application source, generated catalog, or existing design policy was changed. The superseded `docs/ui-quality-workflow-proposal.md` was removed after its adopted guidance was incorporated into the authoritative workflow. No behavior tests were run because this deliverable is a review, not an implementation.

Questions skipped: choosing or implementing a redesign is outside this review-and-survey request.
